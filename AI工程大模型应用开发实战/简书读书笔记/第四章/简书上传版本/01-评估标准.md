# 第四章（1/3）：评估标准——怎样判断模型满足应用要求

第二章讨论过一个问题：输出JSON，并不意味着内容可靠。第三章接着介绍功能正确性、参考相似度、AI裁判和比较评估。读到第四章，我开始把这些方法放回自己的应用：究竟需要检查哪些东西，才能说这个模型满足要求？

继续用前面的企业知识库助手作例子。一个回答可能字段完整、语气友好，却引用了过期的报销制度。如果只检查格式，我们会把它当成成功；如果只看用户是否满意，也可能漏掉错误。评价之前，得先把“好”的含义说清楚。

> 本篇对应Chip Huyen《AI工程：大模型应用开发实战》导言与4.1。知识库助手为贯穿全系列的假设案例，图表自绘；后续研究查阅于2026年10月17日。

**第四章三篇：** ①评估标准 → ②模型选择 → ③设计评估流水线。

## 4.1 评估标准

作者提出“评估驱动开发”：在构建应用之前，先定义评估标准。它让我重新理解第一章的成功标准——“希望用户更方便”需要继续落实到任务、可接受的结果和失败代价上。

比如，知识库助手需要根据当前有效制度回答问题、提供支持结论的出处、在缺少资料时说明限制，并在可以接受的时间内完成。不同要求需要不同证据，一个笼统的满意度分数很难代替它们。

### 4.1.1 领域特定能力

领域能力首先回答：模型有没有完成任务的基础？编程助手需要理解代码，法律文档助手需要处理相关概念，企业知识库助手则要理解公司术语、规则及其适用条件。

这与第二章的数据讨论相连。模型擅长通用中文，并不能直接证明它理解企业内部的简称；输入了相关资料，也需要验证它能否正确使用。

原书介绍了通过选择题、分类和功能正确性评估能力的方式。选择题便于核对答案，也容易建立随机猜测的基线；生成代码则可以运行测试。但识别正确选项与独立生成有效答案是两种任务，应用需要后者时，还应直接检查实际输出。

对于生成的SQL，除了查询结果，还可能需要检查运行时间和内存。类似地，知识库回答即使结论正确，若遗漏关键条件，仍可能误导使用者。领域能力的定义应当贴近最终任务。

### 4.1.2 生成能力

流畅性关注表达是否自然，连贯性关注内容组织是否合理。这些指标仍有价值，但阅读体验良好的文字，也可能缺少事实依据。本节我最关注事实一致性和安全性。

#### 事实一致性

原书区分了两种验证情境：局部事实一致性是对照明确提供的上下文；全局事实一致性则需要对照外部知识和可靠信源。

假设提供给模型的旧制度写着“住宿上限500元”，它回答“上限500元”，与这份资料一致。如果当前有效制度已改为600元，这个回答仍不适合回答“现在能报多少”。**资料一致性与资料本身是否有效，需要分别检查。** 这里的金额仅为例子。

验证可以从完整回答进一步细化到具体陈述。例如，“所有员工出差都能报销600元”至少涉及适用人群、金额和条件。把它拆开，就能发现资料可能只支持某一类员工和特定城市。

*图2：自绘，参考原书4.1.2的陈述拆分与证据核查思路。示例制度为假设，不代表实际企业规定。*

原书介绍的自我验证，会比较多次生成的响应是否一致；知识增强验证则借助检索或搜索结果核查陈述。两者都需要看清边界：多个答案一致，可能共享同一错误；搜索到一篇支持材料，也还要判断来源、日期和适用范围。

当问题与上下文可以明确对照时，可以检查“蕴含、矛盾、中立”：资料支持这个结论，资料与结论冲突，还是资料不足以判断。第三章介绍的AI裁判可以协助分类，但判断依据需要可追溯，不能只留下一个分数。

#### 安全性

原书讨论了有害内容、歧视、刻板印象和意识形态偏差。对于企业助手，我还会结合业务检查权限和信息边界：回答是否暴露无权查看的内容，是否把建议写成未经授权的决定。

这些是不同类型的失败，适合分别整理样本。有害内容检测模型或AI裁判可以提供信号，访问权限则还需要系统层面的控制。把检查位置说清楚，才能知道哪个组件应承担责任。

### 4.1.3 指令遵循能力

模型知道答案，与模型按照要求回答，需要两份证据。比如要求输出固定字段、只依据给定材料、缺少证据时返回“资料不足”，都属于需要单独检验的行为。

原书介绍的IFEval关注可自动验证的要求，如关键词、长度和格式；InFoBench把更宽泛的指令拆成若干判断标准。对我最有帮助的是这种拆解方式：把“请给出可靠回答”改成几个可以核对的问题。

角色扮演也是指令的一种。知识库助手可以使用服务人员的语气，但不应因此表现得像拥有最终审批权。评估角色时，既要看表达风格，也要看它使用的知识和承担的职责是否合适。

这里还能接回第二章：结构约束帮助解决格式问题，字段中的金额、条件和引用仍要继续核查。

### 4.1.4 成本和延迟

一个模型即使回答质量高，如果用户等待过久，或每次任务的总开销无法承受，也可能不适合应用。

延迟要明确口径。首个token响应时间反映开始等待多久，完整任务耗时反映多久才能拿到可用结果；加上检索、工具和评估后，两者可能与单次模型调用明显不同。比较时还要记录输入长度、输出长度和并发条件。

成本同样需要放回整个流程。API调用、检索、重试、裁判和人工复核都可能产生开销；自托管还涉及设备、运行利用率和维护投入。低调用单价，未必对应低任务成本。

我的做法会是先确定硬性要求，再比较满足要求的方案。例如，某类敏感信息必须隔离，不能用更高的平均回答质量来抵消这项失败；在合格方案之间，才进一步权衡质量、费用和等待时间。

## 延伸阅读与个人思考

2025年12月，Google DeepMind发布FACTS Benchmark Suite，分别关注提供文档后的事实依据、内部知识、搜索和多模态输入。这让我更清楚地看到：事实性指标应附带任务条件，闭卷问答与根据资料作答，测量的内容并不相同。[官方介绍](https://deepmind.google/blog/facts-benchmark-suite-systematically-evaluating-the-factuality-of-large-language-models/)

回到知识库助手，我会先写出这样一张验收表，再选择具体方法：

| 应用要求 | 应当记录的证据 |
| --- | --- |
| 结论有依据 | 支持结论的原文及资料版本 |
| 重要条件完整 | 人群、范围、时间及例外是否遗漏 |
| 信息不足时恰当回应 | 是否说明缺口，是否凭空补全 |
| 行为符合职责 | 输出格式、信息边界与授权要求 |
| 使用代价可接受 | 完整任务的费用与延迟分布 |

第一章让我明确要解决什么问题，第二章帮助我理解错误可能从哪里来，第三章提供了评价方法。第四章的第一步，是把这些认识写成可检查的应用要求。下一篇就用这些要求，讨论怎样缩小模型选择范围。
